# 1. PRODUCT

## Name

**EvidenceOps**

Subtitle:

**Production Document Intelligence & RAG Quality Workbench**

## One-line pitch

Turn PDFs and DOCX files into cited structured data and evidence-bound AI answers, with human review, version history, regression testing and full run observability.

## Product purpose

EvidenceOps demonstrates what production-grade document AI should look like after moving beyond a basic extraction script or RAG chatbot.

The application must:

1. ingest PDF and DOCX documents;
2. preserve their original source;
3. parse them into source-addressable blocks;
4. extract structured information with an LLM;
5. capture provenance for every extracted value;
6. independently verify extracted values;
7. run deterministic validation;
8. calculate confidence programmatically;
9. route uncertain output to human review;
10. preserve corrections through immutable version history;
11. index approved/current documents for hybrid RAG;
12. generate evidence-bound answers and first drafts;
13. refuse unsupported questions;
14. evaluate extraction, provenance, retrieval, answers and review routing against a golden set;
15. compare evaluation runs to a baseline;
16. detect regressions;
17. track retries, failures, latency, token usage and cost;
18. resume safely after failure;
19. generate a complete HTML QA report for every evaluation/demo run.

The central product principle is:

**Model output is not trusted merely because a model produced it.**

Every important output should be inspectable and traceable.

# 5. SUCCESS CRITERIA

The project is finished only when the following measurable conditions pass.

## Corpus processing

Process a deterministic fixture corpus of 20 source files.

Required composition:

* 16 PDF files;
* 4 DOCX files;
* 16 logically unique base documents;
* 2 exact duplicates;
* 2 corrected source versions.

Requirements:

* all valid text documents ingest;
* exact duplicates are detected;
* duplicate uploads do not repeat paid LLM processing;
* corrected documents create new source versions;
* prior versions remain accessible;
* rerunning a successful document does not create duplicate records;
* every processing run reaches an explicit terminal state.

Allowed terminal states:

* `completed`
* `completed_with_review`
* `failed`

No run may remain silently stuck.

## Extraction quality

Target metrics:

* scalar exact accuracy >= 95%;
* list/object extraction micro-F1 >= 90%;
* document classification accuracy >= 95%;
* provenance validity >= 98%.

## Review

* review recall on intentionally uncertain/incorrect fields >= 90%;
* review precision >= 75%;
* every field below the auto-approval threshold enters review or blocked review;
* human correction creates a new immutable record version.

## RAG

Golden RAG set contains exactly 40 questions:

* 20 single-document answerable questions;
* 10 cross-document answerable questions;
* 10 deliberately unanswerable questions.

Targets:

* retrieval Recall@5 >= 90%;
* citation precision >= 95%;
* evidence-supported answer rate >= 95%;
* unanswerable refusal accuracy >= 95%;
* average semantic answer score >= 0.90.

## Reliability

Implement an intentional failure-injection mechanism.

A failure injected after extraction must prove that:

1. completed previous steps remain persisted;
2. the failed step is recorded;
3. retries occur;
4. the run can resume;
5. the original file does not need re-uploading;
6. completed parsing is not repeated;
7. completed paid model output is not repeated when its idempotency key is unchanged.

# 11. INGESTION

Upload accepts:

* PDF;
* DOCX.

Maximum file size:

10 MB.

Maximum PDF pages:

50.

At upload:

1. validate MIME/extension;
2. compute SHA-256 on raw bytes;
3. check existing hashes;
4. determine logical document;
5. determine whether duplicate or new version;
6. persist file;
7. create DB records;
8. start processing run.

## Duplicate rule

If identical hash already exists:

* do not create a new document version;
* do not parse;
* do not call an LLM;
* log `duplicate_detected`;
* return link/reference to existing version.

## Corrected version rule

If logical key already exists but raw hash differs:

* create next `version_number`;
* set previous `is_current=false`;
* set new `is_current=true`;
* populate `supersedes_version_id`.

# 18. INDEPENDENT VERIFICATION

Do not use extractor self-confidence.

## Verification system prompt

You are EvidenceOps Verifier.

You independently verify a candidate extracted value against its cited source evidence and surrounding context.

Do not trust the candidate simply because another model produced it.

Use only the source material supplied in this request.

Classify the candidate as:

SUPPORTED:
The candidate is directly supported by the source.

PARTIALLY_SUPPORTED:
The source supports the core meaning, but the candidate adds, omits, normalizes, or resolves something that is not completely explicit.

UNSUPPORTED:

5. Do not use external knowledge.
6. If a corrected value can be stated exactly from the supplied evidence, return it.
7. evidence_specificity must be between 0 and 1:

   * 1.0 = direct, explicit support
   * 0.75 = clear contextual support
   * 0.4 = broad or weak support
   * 0.0 = no support
8. Return only JSON matching the schema.

# 19. CONFIDENCE FORMULA

Compute confidence in application code.

Do not ask an LLM for final confidence.

Formula:

```text
confidence =
0.30 × evidence_exact_match
+ 0.20 × deterministic_validation
+ 0.25 × verifier_support
+ 0.15 × cross_pass_agreement
+ 0.10 × evidence_specificity
```

## `evidence_exact_match`

* `1.0` if normalized evidence quote exists in the cited source block;
* `0.0` otherwise.

## `deterministic_validation`

* `1.0`: all validators pass;
* `0.5`: warnings only;
* `0.0`: material failure.

## `verifier_support`

* supported = 1.0
* partially supported = 0.5
* unsupported = 0.0

## `cross_pass_agreement`

* exact normalized candidate/verifier agreement = `1.0`;
* semantically equivalent formatting-only difference = `0.75`;
* materially different corrected value = `0.0`.

For deterministic fields such as monetary amounts and normalized dates, formatting normalization should occur before equality testing.

## `evidence_specificity`

Use verifier output directly:

* direct evidence = 1.0
* contextual evidence = 0.75
* weak evidence = 0.4
* no evidence = 0.0

# 50. TESTS

Create comprehensive tests.

## Unit tests

### Hashing/versioning

* identical file → identical hash;
* changed bytes → changed hash;
* duplicate does not create new source version;
* corrected file creates next version;
* old current version becomes false.

### PDF parsing

* pages separated correctly;
* locator correct;
* corrupt file fails;
* scanned/low-text detection works.

### DOCX parsing

* paragraphs ordered;
* source positions preserved.

### Chunking

* chunk target approximately 800;
* overlap approximately 120;
* source references preserved;
* documents never mixed.

### Evidence validation

* exact evidence succeeds;
* normalized whitespace succeeds;
* hallucinated quote fails;
* wrong source block fails.

### Date validation

Test:

* ISO date;
* `4 Sept. 26`;
* invalid date.

### Currency validation

Test valid/invalid values.

### Confidence

Test exact numerical outputs.

Include:

* 1.0;
* exact 0.86;
* exact 0.65;
* contradiction;
* unsupported evidence.

### Routing

Test thresholds exactly.

### Retrieval scoring

Test vector/lexical combination.

### Version filtering

Current versions excluded/included correctly.

### Cost calculation

Use deterministic token fixture.

## Integration tests

* upload → storage → DB;
* ingest → parse → source blocks;
* extraction → validation;
* extraction → verifier;
* verifier → confidence;
* confidence → review;
* review action → new record version;
* chunks → embedding persistence;
* question → retrieval → answer;
* answer → citations;
* eval → metrics;
* eval → regression result;
* QA report generation;
* failed step → dead letter;
* retry → successful resume.

Mock OpenAI where necessary so tests are deterministic and inexpensive.

## E2E tests

### Clean extraction

Upload clean fixture.

Expect:

* complete;
* structured record;
* citations;
* no unnecessary review.

### Ambiguous monetary amount

Expect:

* review item;
* evidence shown;
* edit & accept;
* new record version.

### Duplicate

Upload same file twice.

Expect:

* duplicate notice;
* no second extraction.

### Corrected source

Upload v1 then v2.

Expect:

* version chain;
* v2 current;
* v1 retained.

### Answerable RAG

Expect correct cited answer.

### Unanswerable RAG

Expected exact response:

`Insufficient evidence in the indexed corpus.`

### Failure/resume

Inject failure at verify.

Expect:

* extract succeeded;
* verify fails/retries;
* after injection removed, verify resumes;
* extraction output reused.

### Regression

Introduce deterministic bad mocked output.

Expect:

* evaluation regression;
* QA report flags it.
